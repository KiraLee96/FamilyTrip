## P1 · 阻断发版

### BUG-001 回忆墙照片单击即删除，无二次确认、无撤销

- **状态**：CONFIRMED（已实测复现，有截图为证）
- **环境**：`ENV-H5-MOCK`；代码位置 `apps/client/src/pages/MemoryPage.tsx:160` `PhotoCell`
- **前置**：回忆墙已有 4 张照片
- **复现步骤**：
  1. 打开 `/pages/MemoryPage`，照片网格显示 4 张
  2. 单击任意一张照片（用户本意通常是查看大图）
  3. 观察网格与网络请求
- **实际结果**：照片格 4 → 3，直接调用 `DELETE /media/:id` 删除成功，全程**无任何确认弹窗**。截图 `qa/reports/probe/p1-memory-before.png` / `p1-memory-after.png`，证据 `probe-report.json`。
- **期望结果**：删除前必须二次确认（与行程删除、清单删除口径一致），或改为「点开大图 → 图内删除」。
- **根因**：`PhotoCell` 把整格 `onClick` 绑到 `remove()`，与注释「长按删除角标」不符；删除角标 `.photo-cell__del` 只是视觉元素，未绑定事件。
- **影响**：数据丢失 + 极易误触。任何家庭成员点照片想看大图，照片即被永久删除。
- **建议**：整格点击改为打开预览；删除收敛到角标并加 `Taro.showModal` 确认。删除后提供 5 秒撤销（软删 + 延迟提交）更稳。

### BUG-002 行程详情照片删除无二次确认

- **状态**：CONFIRMED（代码审查）
- **环境**：代码位置 `apps/client/src/pages/TripDetailPage.tsx:1932` `PhotoTab`
- **复现步骤**：
  1. 进入行程详情 → 照片 tab
  2. 点任意照片右上角 `×` 角标
- **实际结果**：`onClick={() => void remove(p.id)}` 直接删除，无确认、无 Toast。失败时静默（catch 空实现），用户不知道删没删成。
- **期望结果**：与 BUG-001 同口径——二次确认 + 删除结果反馈。
- **影响**：误触即丢照片；失败无反馈导致重复操作。
- **建议**：抽一个共用的 `confirmDeleteMedia(id, onDone)`，两处复用。

## P2 · 与需求不符 / 功能缺失

### BUG-003 出行日期冲突校验完全缺失

- **状态**：PENDING-SCOPE
- **需求**：《需求概要》§4.3 —— 判定条件「日期区间重叠 ∧ 参与成员重叠」，两者同时满足才提示；且仅温和提醒、不硬拦截
- **环境**：`apps/client/src/pages/TripCreatePage.tsx` `submit()`
- **复现步骤**：已有 10-01~10-05 行程且含成员甲 → 新建 10-03~10-07 并勾选成员甲 → 创建
- **实际结果**：直接创建成功，无任何提示。`submit()` 内只有名称必填、日期先后、familyId 三项校验。
- **期望结果**：弹出「XX 这期间已有出行，可能存在冲突」，确认后仍可创建。
- **影响**：同一批人被重复排期，需求定义的核心防错能力为零。
- **建议**：提交前拉 `listTrips()` 做区间交集 + 成员交集判断（纯前端即可，不必等服务端）。

### BUG-004 多币种记账能力缺失（币种 / 汇率快照 / 双币展示 / 手动覆盖）

- **状态**：PENDING-SCOPE
- **需求**：《需求概要》§5.2 + 决策 13 —— 支持录入外币、汇率录入时快照固化、明细双币展示、允许手动覆盖结算汇率
- **环境**：`apps/client/src/pages/TripDetailPage.tsx:1691` `ExpenseForm`、`:1649` 明细行
- **复现步骤**：花销 tab → 记一笔 → 查看表单字段与明细展示
- **实际结果**：
  1. 表单字段只有 名称 / 金额（元）/ 日期 / 类目 / 备注，**无币种选择、无汇率输入**；
  2. 明细行写死 `¥{e.amount}`，币种非 CNY 时会显示成人民币符号且不折算；
  3. 汇率工具 `utils/fx.ts`、`hooks/useFxRate.ts` 已存在但未接入花销链路。
- **期望结果**：可选币种 → 自动取当日汇率并固化为快照 → 明细双币展示（`¥10,000 JPY ≈ ¥480`）→ 汇总统一按基准币 → 支持手动覆盖。
- **影响**：海外/跨境出行记账不可用（这是需求里明确的差异点能力）。
- **建议**：`createExpense` 契约已支持 `currency`，后端 fx 域也已就绪，缺的纯粹是客户端 UI + 折算展示。

### BUG-005 心愿「一键带入」生成行程草稿缺失

- **状态**：PENDING-SCOPE
- **需求**：§3.4 在心愿池点「安排」→ 自动带入预算/时长/时间 → 生成草稿并跳年度规划；决策 5「生成草稿后需人工确认才落库」
- **环境**：`apps/client/src/pages/WishPoolPage.tsx`
- **实际结果**：心愿卡只有投票按钮；页尾仅有文案「票数最高的一条，可以直接转成行程草稿」，无对应入口。
- **期望结果**：心愿卡提供「安排」操作，带入字段生成草稿。
- **影响**：心愿池 → 年度规划的价值链路断在第一跳，心愿池沦为纯留言板。
- **建议**：先做最小闭环——「安排」→ 跳 `/trips/new` 并预填标题/目的地/预算，比全自动草稿成本低且不违反「人工确认」决策。

### BUG-006 心愿字段不完整

- **状态**：PENDING-SCOPE
- **需求**：§3.2 字段表（目的地、想去理由、属性标签多选、预算区间、最佳出行时长、最佳出行时间+气候说明、参考图/链接、票数）
- **环境**：`WishPoolPage` 提心愿抽屉；`api/types.ts` `Wish`
- **实际结果**：仅支持 标题 + 补充说明（note）+ 已存在的 tags 展示。属性标签无选择器、预算区间/时长/季节/气候说明/图片/链接全部缺失。
- **期望结果**：按 §3.2 补齐可填字段。
- **影响**：投票决策缺少依据（不知道要花多少钱、几天、什么季节去）。

### BUG-007 心愿状态流转缺失

- **状态**：PENDING-SCOPE
- **需求**：§3.3 `想去 → 已安排 → 已完成 / 已放弃`，且**不可删除只能改状态**
- **环境**：`WishPoolPage`；`api/types.ts` 状态枚举为 `OPEN / ADOPTED / ARCHIVED`
- **实际结果**：只有「待投票 / 已成行」两个分组，无任何改状态入口；`ADOPTED` 由谁、何时置位不明。
- **期望结果**：可标记为已安排/已完成/已放弃；无删除入口。
- **影响**：心愿池无法自然收敛，过时心愿永远留在待投票列表。

- **影响**：规划出行时看不到「哪天能连休」，年度规划的核心决策依据缺失。

## P3 · 体验与口径

### BUG-013 物品缺图片字段

- **状态**：PENDING-SCOPE
- **需求**：§6.2 物品字段 = 名称、类别、图片
- **实际**：`ItemsPage` 增改表单只有名称/分类/数量/备注，无图片。
- **影响**：穿搭挑选靠文字，找东西慢。

### BUG-014 首页月份时间轴不区分年份

- **状态**：OPEN
- **环境**：`HomePage.tsx:224` `MonthRail` —— `set.add(Number(t.startDate.slice(5, 7)))`
- **实际**：全年 12 个圆点只看月，不看年。去年同月的行程也会点亮今年月轨。
- **期望**：仅统计当前年份（或按所选年份）。
- **影响**：年份越久，月轨越失真。

### BUG-015 「同行人数」取的是家庭总人数

- **状态**：OPEN
- **环境**：`HomePage.tsx:135`、`PlanPage.tsx:122` —— `families[0].memberCount`
- **实际**：显示「N 人同行」的 N 是家庭成员数，不是本次行程实际参与人数。
- **期望**：取该行程 `TripMember` 数。
- **影响**：外部成员结伴（需求重点场景）时数字明显错误。

### BUG-016 首页预算卡进度条恒为 100%，总预算显示「待定」

- **状态**：OPEN
- **环境**：`HomePage.tsx:286` `style={{ width: '100%' }}`
- **实际**：无论花多少，进度条满格；文案「已花费 / 总预算」后面跟「待定」。
- **期望**：无预算数据时不应展示完成度进度条（会误导为「已花完」）。
- **影响**：视觉误导，用户误以为预算已耗尽。

### BUG-017 同行成员入队失败被静默吞掉，人数展示不实

- **状态**：OPEN
- **环境**：`TripCreatePage.tsx:173` `catch (e) { console.warn(...) }`；`:115` `memberCount={selectedIds.size + 1}`
- **实际**：`addTripMember` 批量入队失败只打 warn，用户看到的是「N 位家庭成员已加入」（按勾选数算），实际可能一个都没进。
- **期望**：失败要提示「部分成员未能加入，可进入行程后重试」。
- **影响**：创建者以为全家都在行程里，实际只有自己。

### BUG-019 已结束行程仍可复制/分享邀请码加入（待产品确认）

- **状态**：PENDING-SCOPE
- **证据**：`qa/reports/probe/p4-readonly-invite.png` —— 只读行程（FINISHED）页面仍显示「复制 / 分享」按钮，仅隐藏「重置邀请码」与「凭码加入」。
- **相关需求**：§2.4「出行结束后临时家庭关系解除，访问权限自动失效」
- **风险**：外部成员可凭旧码加入一个已归档行程，是否应拦截需产品裁定。代码注释显示「复制/分享保留」是**有意的设计决定**，因此不按缺陷计，登记为待确认项。

## 测试资产缺陷

### TA-001 验收脚本 R2-3 断言过期（非产品缺陷）

- **位置**：`apps/client/.verify/verify-features-v1.cjs:295`
- **现象**：断言 `detailText.includes('来自回忆墙的行程仅可查看')`，实测 FAIL。
- **判定**：**假失败**。截图 `f4-readonly-detail.png` 证实只读横幅存在，但行程 `103` 状态为 FINISHED，`TripDetailPage` 的文案按 `closed` 分支优先渲染「行程已结束，记录转只读：可回看，不能再修改或删除」。
- **附带覆盖盲点**：readonly 与 closed 两个只读来源在同一行程上叠加，脚本无法单独验证 `readonly=1` 分支。建议对一条**未结束**行程补 readonly 用例。
- **建议**：断言改为匹配「转只读」通用文案，或改用 `.readonly-banner` 元素存在性判断。
