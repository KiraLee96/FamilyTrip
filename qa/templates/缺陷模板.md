# 缺陷单模板

> 命名：`缺陷单-YYYY-MM-DD.md`，一轮测试一份。编号 `BUG-001` 起，同轮内不复用。

## 缺陷详情（每条一份）

### BUG-001 〈一句话说清现象〉

- **级别**：P0 / P1 / P2 / P3
- **状态**：OPEN / CONFIRMED（已复现）/ PENDING-SCOPE（需产品确认范围）/ FIXED / VERIFIED
- **环境**：项目 / 版本或 commit / 平台 / 数据源（Mock or 真后端）
- **位置**：`文件路径:行号` 或页面路径
- **关联需求**：§x.x
- **关联用例**：MOD-01

**前置**：具体数据与账号状态

**复现步骤** 1. 2. 3.

**实际结果**：（贴现象 + 截图/日志/请求响应）

**期望结果**：（依据需求，不依据现状）

**根因**：（能定位就写，定位不到写怀疑方向与排查路径）

**影响**：谁会遇到、多久一次、损失是什么

**建议**：（给方案，别只交问题）

**修复记录**：commit / 验证人 / 验证方式

---

## 提缺陷的底线

1. 步骤必须可复现：别人照着点了就能看到同样的结果。
2. 环境必须写全：同一份代码在 Mock 和真后端下表现可能完全相反。
3. 图片/日志/字节三选一，空口描述不予受理。
4. 「功能缺失」和「行为错误」分开记，前者走范围裁定，后者走修复。
