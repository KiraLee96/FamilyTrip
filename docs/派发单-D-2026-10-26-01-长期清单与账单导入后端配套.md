## P0-1 · `PATCH /checklists/templates/:id` 修改长期清单

### 为什么必须要

用户诉求是「**长期维护**」的物品清单。当前后端只支持「建一次、之后不能改」：

- `POST /checklists/templates` 支持一次写入全部条目；
- 但用户第二天想加一双「溯溪鞋」，没有任何端点可写 —— 前端只能提示「暂不可改」。

没有这一跳，「长期维护」这个核心价值等于没落地。

### 契约（按此实现，前端已按最终形态写好）

```
PATCH /api/checklists/templates/:id
Authorization: Bearer <token>
Content-Type: application/json
```

**请求体**

```ts
{
  version: number;                       // 必传，CAS 乐观锁
  name?: string;                         // 1–64 字
  items?: Array<{ name: string; quantity: number }>;  // 整体替换语义
}
```

| 字段      | 规则                                                                                                              |
| --------- | ----------------------------------------------------------------------------------------------------------------- |
| `version` | **必传**；与行内 `version` 不一致 → `409 VERSION_CONFLICT`（与 checklist item / trip 的 CAS 口径一致）            |
| `name`    | 可选，1–64 字，去首尾空格后非空                                                                                   |
| `items`   | 可选，**整体替换**（不是增量合并）；最多 200 条；`name` 1–64 字、`quantity` 1–9999                                |
| 至少一项  | `name` 与 `items` 二者至少给一个，否则 `400 VALIDATION_FAILED`                                                    |
| 写入      | `items` 序列化进 `items_json`（TEXT）；`version = version + 1`；`updated_at = dbNow()`；写 `changeLog(op=UPDATE)` |

**响应**

```json
{
  "code": 0,
  "message": "ok",
  "data": { "template": { "...": "checklistTemplate 行" } },
  "meta": { "updatedAt": "..." }
}
```

**权限**

- `scope = SHARED`：家庭任一成员可改（与 `applyTemplate` 的「任意成员可引用」保持同口径）；
- `scope = PERSONAL`：仅 `ownerId` 本人（或该成员的代管人）可改；
- 越权与不存在**同形**：统一 `404 / 4040 资源不存在`（沿用 access-policy 的「越界与不存在逐字节一致」）。

**验收用例**

1. 改名称 → 再 `GET /checklists/templates` 读回新名称，`version` 自增 1；
2. 传 `items: []` → 条目清空（模板本身保留）；
3. 用旧 `version` 再改一次 → `409`，且库内数据未被覆盖；
4. 改别人的 PERSONAL 模板 → `404`（不是 403）；
5. `items` 传 201 条 → `400`。

## P0-2 · `DELETE /checklists/templates/:id` 删除长期清单

```
DELETE /api/checklists/templates/:id
→ { "code": 0, "message": "ok", "data": null, "meta": { "updatedAt": "..." } }
```

| 项                 | 规则                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| 删除方式           | **软删**（`deleted_at = dbNow()`），与域内其它 DELETE 一致                                           |
| 已引用的行程清单项 | **不级联删除**。`trip_checklist_item.template_id` 保留原值（用于追溯来源），只是模板不再出现在列表里 |
| 幂等               | 已删的模板再删 → `404 / 4040`（与「不存在」同形，不暴露「曾经存在」）                                |
| 权限               | 同 P0-1                                                                                              |
| 审计               | 写 `changeLog(entityType='checklist_template', op='DELETE')`                                         |

**验收用例**

1. 删掉「家庭出行常用」→ 列表少一套，但行程里由它引用来的清单项仍在、仍可勾选；
2. 非本家庭成员删 → `404`；
3. 删后 `GET /checklists/templates` 不含该 id。

## P1-1 · `POST /expenses/batch` 批量记账

### 现状

前端导入账单时逐行 `POST /expenses`（串行，保证失败溯源）。一轮「暑期 20 天」账单
常有 60–120 笔，串行就是 60–120 次往返 + 幂等键开销，弱网下体验差。

### 建议契约

```
POST /api/expenses/batch
{
  "tripId": "101",
  "familyId": "10",
  "rows": [
    { "title": "栈桥咖啡", "amount": "42.50", "currency": "CNY",
      "category": "餐饮", "spentAt": "2026-10-03", "note": "导入" }
  ]
}
```

| 项          | 规则                                                                                |
| ----------- | ----------------------------------------------------------------------------------- |
| `rows` 上限 | 200（超过按 400 拒，让客户端分批）                                                  |
| 语义        | **部分成功**：逐行独立事务，返回每行结果；不因一行失败回滚整批                      |
| 响应        | `{ data: { created, failed, results: [{ ok, error? }] } }`                          |
| 幂等        | 整批带一个 `requestId`；同 `requestId` 重放返回首次结果（现有幂等中间件可直接复用） |
| 限流        | 单用户 1 次/秒（导入是低频操作，收紧没代价）                                        |

> 前端已按「逐行串行」实现并上线可用，本端点属**性能优化**，不改变客户端调用方式
> （`ApiClient.createExpensesBatch` 签名不变，只换实现层）。

## P1-2 · `GET /checklists/templates` 回包补 `items`

现状返回的是原始行，条目在 `itemsJson`（字符串）里：

```json
{ "id": "501", "name": "家庭出行常用", "itemsJson": "[{\"name\":\"身份证\",\"quantity\":4}]" }
```

前端已在 `api/http.ts` 的 `toChecklistTemplate` 里解析并做脏数据兜底（解析失败 → 空数组），
所以**不阻断**。但建议后端直接回解析后的数组，理由：

1. 每个客户端（小程序 / H5 / 将来的原生）都要重复实现一次 `JSON.parse` + 容错；
2. `itemsJson` 一旦有历史脏数据（`null` / 手写非 JSON），只有后端能统一修。

```json
{ "id": "501", "name": "家庭出行常用", "items": [{ "name": "身份证", "quantity": 4 }], "itemsJson": "[...]" }
```

> 建议**新增 `items` 字段、保留 `itemsJson`**（纯加法，老客户端不受影响）。

## P2-1 · 邀请码未命中要有可区分的错误码

用户反馈里「家庭邀请码分享之后无效」，前端已修掉两类前端原因（复制通道单一、
分享未回填邀请码）。但**码本身错了**时，前端无法给出有用提示：

- 现状：`family.service.join` 未命中 → `4040 资源不存在`，与「路径写错」「家庭已解散」同形；
- 建议：`4041 INVITE_CODE_INVALID` + `message: '邀请码无效或已失效'`。

前端会据此把提示从「资源不存在」改成「邀请码无效，请让家人重新发一次」。
`JoinFamilyPage` / `JoinTripPage` 都按这个码分流，改动只在文案映射层。
