### 2.1 抓堆栈（最直接）

复现一次，取该时刻前后 2 分钟的进程日志：


500 的信封是全局兜底生成的，**堆栈只存在于日志里**，客户端看不到。需要的是：


### 2.2 确认生产部署版本

```bash
cd <server-deploy-dir> && git rev-parse --short HEAD
```

仓库当前 HEAD：`0302570`。若生产不是这个 commit，请先说明——排查方向会完全不同
（例如库里缺某列、或 `dist/` 是旧构建）。

### 2.3 确认两张表在生产库存在且列齐

`finish` 会写两张表，任一缺列都会 500：

```sql
SHOW TABLES LIKE 'audit_log';

DESC audit_log;   -- 关注 detail(JSON) / severity / reason / target_type / target_id
```

### 2.4 用真 MySQL 复现一次（决定性）

内存驱动测不出 Prisma/MySQL 层异常。建议对**生产数据副本**执行：

```bash

  -H "Authorization: Bearer <该行程主导者的 token>" \
  -H "Content-Type: application/json" \
  -d '{"version": <该行程当前 version>}'
```

若返回 500，日志会给出确切字段/约束名；若返回 200，说明是**生产进程状态**问题
（如连接池耗尽、进程重启中），需要在 2.1 的日志里找。

## 4. 前端本轮的改动（非根因修复，请勿混淆）

`apps/server/src/domains/trip/trip.service.ts` · `finishInternal`：

```diff
-        actualJson: opts.actual ? JSON.stringify(opts.actual) : (t['actualJson'] ?? null),
+        // 只在真的传了 actual 时才写这一列（避免把读出的旧快照回写、覆盖并发写入）
+        ...(opts.actual !== undefined ? { actualJson: JSON.stringify(opts.actual) } : {}),
```

两条理由：① 没传 `actual` 时把旧快照原样写回属无谓列写；② 并发下 `t` 可能是旧快照，
会把别人刚写入的 `actual_json` 覆盖回 null。**与本次 500 无因果关系**（已实验证伪）。

客户端另加了一层可定位性：`标记完成` 失败时的提示会带上后端 code
（`服务内部错误（code 5000）`），下次可直接把 code 报给后端。

## 5. 回归缺口（建议补，防复发）

现有服务端用例全部跑在**内存驱动**上，它接受 `null`、不校验 SQL 方言，
所以「Prisma 参数校验」「MySQL 约束」这类问题在 CI 里永久隐形。

建议：

- 增加一条**真驱动**用例（CI 里起 MySQL 容器 + 跑迁移），至少覆盖：
  `createTrip`（不传 destinations）、`finish`（不传 actual）、`PATCH /trips/:id`；
- 或者给 CI 加一道「生产同版本 Prisma client 参数校验」冒烟，成本更低但覆盖面窄。
