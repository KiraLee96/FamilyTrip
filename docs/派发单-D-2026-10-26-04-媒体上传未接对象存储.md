## 0. 一句话结论

上传链路（`presign → 直传 → confirm`）的**中间那跳从来不存在**：

- 仓库里**没有任何对象存储适配器**（无 COS / OSS / S3 SDK 依赖）；
- `signUpload` 这个注入口**全仓 0 处注入**；
- 因此 `POST /media/presign` 永远返回占位地址 `https://upload.local/<fileKey>`；
- 客户端 `Taro.uploadFile` 打这个域名 → DNS 解析失败 → 界面提示「上传失败」/「头像更新失败」。

**这个问题与「代码没部署」无关**。即使后端把本轮所有新代码部署上线，只要 `signUpload` 仍未注入，
上传依然是坏的。上一单（D-2026-10-26-03）解决的是「代码没上线」，本单解决的是「代码里缺这块」。

另外，`.env.example` 里已经写明了这是已知延后项：

```
# 媒体公网访问基址：media list 会把 fileKey 拼成可访问 URL 返回（方案 A）。
# 生产接对象存储 / CDN 公网域名；本地联调用占位域名即可（图片不可达，仅验证契约）。
MEDIA_PUBLIC_BASE_URL=https://media.local
```

注释承认「图片不可达，仅验证契约」—— 也就是说契约验过了、实现留空了。**现在需要补齐实现。**

## 4. P0 · 三种落地方案（推荐 A）

有一个约束必须先说清，它决定方案选型：

> **`Taro.uploadFile` 只能发 `multipart/form-data` POST，不能发 PUT 裸流。**
> 小程序端也没有 `fetch`/`Blob` 可用，绕不过去。
> 所以「presign 一个带签名的 PUT URL 让客户端 PUT 上去」这条路，**在 Taro 小程序端走不通**。

|                      | 方案 A（推荐）                                                                                           | 方案 B                                                                    | 方案 C                             |
| -------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------- |
| 做法                 | presign 返回**自家收单端点**地址，服务端收流后 `putObject` 到桶                                          | presign 返回桶的 **POST Object 表单**地址 + `formData` 字段，客户端直传桶 | 发 STS 临时密钥，客户端用 SDK 直传 |
| 前端改动             | **0 行**（现有 `uploadFile` + `presign.headers` 已够）                                                   | 1 行：`uploadFile({ ..., formData: presign.formData })`                   | 大：小程序端要引入 SDK             |
| 后端改动             | 新增一个 multipart 端点 + 一个 `signUpload` 实现                                                         | 新增一个 `signUpload` 实现（生成 policy/签名）                            | 新增 STS 服务 + 桶策略             |
| 契约变更             | 无                                                                                                       | 响应新增可选 `formData`（纯加法）                                         | 大                                 |
| 文件是否过服务端     | 是（多一跳）                                                                                             | 否（直连桶）                                                              | 否                                 |
| 服务端可做 EXIF 剥离 | **天然可以**（字节在手）                                                                                 | 不能（需另调 strip-exif）                                                 | 不能                               |
| 契合现有设计         | **高** —— media 域已有 `putObject?: (fileKey, data, mimeType) => Promise<void>` 选项，正是为这条路预留的 | 中                                                                        | 低                                 |

**推荐 A 的理由**：`putObject` 这个注入口已经在 `MediaDomainOptions` 里了（`stripExif` 用它回写），
说明作者本来就是按「服务端持有字节」设计的。补 A 只是把这个能力接到「接收客户端上传」这个入口上，
不引入新契约、不动客户端、顺带解决 EXIF 隐私（PRD 里有要求）。

### 4.1 方案 A 的接口形态

`signUpload` 返回的 `uploadUrl` 指向自家端点，签名信息放 query（因为 `uploadFile` 的 `header`
来自 presign 响应，用来传 Bearer token 不合适 —— URL 自带签权更省事）：

```ts
// 返回
{
  uploadUrl: `${SELF_PUBLIC_BASE}/api/media/upload?fileKey=${encodeURIComponent(fileKey)}&exp=${exp}&sig=${sig}`,
  headers: {},          // 不需要额外头
  expiresIn: 900,
}
// sig = HMAC-SHA256(`${fileKey}:${exp}`, MEDIA_UPLOAD_SECRET) 的 hex
```

**必须用 express 原生路由挂载**，不要走 `RouteSpec` —— dispatcher 的响应契约是 JSON 信封，
而这里要接收 `multipart/form-data` 并流式读 body，两者不兼容（本地 dev 通道已验证这条路可行）。

骨架：

```ts
// 收流 → 校验签名 → putObject → 返回 JSON
express.post('/media/upload', async (req, res) => {
  const { fileKey, exp, sig } = req.query as Record<string, string>;
  if (!verifySig(fileKey, exp, sig)) return res.status(403).json({ code: 4030, message: '签名无效或已过期' });
  const { buffer, mimeType, byteSize } = await readSingleFilePart(req); // 复用 busboy / multer
  if (byteSize > MAX_BYTES) return res.status(400).json({ code: 4000, message: '文件超过 50MB' });
  await putObject(fileKey, buffer, mimeType); // ← 已有的注入口
  return res.status(200).json({ code: 0, message: 'ok', data: { fileKey, byteSize } });
});
```

### 4.2 方案 B（若选直传桶）

`presign` 响应扩一个字段（纯加法，老客户端忽略即可）：

```jsonc
{
  "uploadUrl": "https://<bucket>.cos.<region>.myqcloud.com",
  "headers": {},
  "formData": {
    "key": "f/...",
    "policy": "...",
    "q-sign-algorithm": "sha1",
    "q-ak": "...",
    "q-sign-time": "...",
    "q-signature": "...",
    "x-cos-security-token": "...",
  },
  "expiresIn": 900,
  "fileKey": "f/...",
}
```

前端改 1 行（`apps/client/src/utils/upload.ts` · `uploadOne()`）：

```diff

+    ...(presign.formData !== undefined ? { formData: presign.formData } : {}),
```

## 7. P2 · `purpose` 未透传：头像与照片混在同一池

前端 `apps/client/src/api/http.ts` 已经传了 `purpose`：

```ts
...(input.purpose !== undefined ? { purpose: input.purpose } : {}),   // presign 与 confirm 都传
```

后端两处都没接：

1. `presignUploadSchema`（`media.schema.ts`）无 `purpose` 字段 → Zod 默认 strip，静默丢弃；
2. `media.service.ts` · `presign()` 落 `filePending` 时硬编码 `purpose: 'MEDIA'`；
3. `confirmUploadSchema` 同样无 `purpose`。

影响：

- 头像文件与家庭照片**同池**，`fileKey` 前缀都是 `f/<familyId>/`；
- 孤儿清理、配额统计、按用途过滤都无法区分；
- 头像也不必要地绑定了 `familyId`（一个没家庭的用户理论上传不了头像）。

建议：

```ts
// presign / confirm schema 都加
purpose: z.enum(['MEDIA', 'AVATAR']).default('MEDIA'),

// fileKey 前缀分流
const prefix = purpose === 'AVATAR' ? `a/${userId}` : `f/${familyId}`;
```

优先级低于 P0（不影响能不能传），但补 P0 的时候顺手做掉成本最低。

## 8. 验收自检（部署后照做）


## 9. 回归缺口（为什么这个问题没被任何测试拦到）

1. **服务端测试全跑内存驱动**，且 `signUpload` 未注入时恒返占位地址 —— 测试里 presign 永远是「成功」的；
2. **客户端 `uploadOne()` 有这段跳过逻辑**：

   ```ts
   if (presign.uploadUrl) {   // ← 占位地址是 truthy，不会跳过；但 H5 验收跑的是 Mock 客户端
     await Taro.uploadFile({ ... });
   }
   ```

   而 H5 无头验收用的是 **Mock 客户端**（直接造 asset，不碰真实上传），所以「假成功」；

3. 结果：**上传整条链路在建库以来从未被真实执行过**。

建议加一条集成测试（真桶或 minio 容器）：`presign → upload → HEAD 可读 → confirm → list.url 可访问`。
与 D-2026-10-26-03 §5 提的「CI 需要真 MySQL」是同一类缺口 —— **内存驱动掩盖了所有外部依赖问题**。
