## P0-1 · 行程日期结束后自动变「已完成」

### 用户原话

> 「行程的时间结束后要自动变成已完成，已完成的行程不能编辑信息只能添加或删除回忆照片」

### 现状（已核查代码）

- `trip.service.finish()` 只提供**手工**完结：校验主导者/创建者 → CAS 改 `status=FINISHED` →
  全员 `tripMember.accessLevel` 转 `HISTORICAL_READONLY` → 写 changeLog + audit。
- 全仓 **无** `setInterval` / `cron` / `schedule` / 调度入口（`grep` 已确认）。
- 因此行程过了 `end_date` 后 status 永远停在 `PLANNED`/`ONGOING`，
  成员 accessLevel 仍是 `ACTIVE` —— 数据层面「这趟行程没结束」。

### 前端已做的兜底（不是替代方案）

界面按日期**派生**显示「已完成」徽章，并在详情页给一条明确提示 + 「标记完成」按钮
（`POST /trips/:id/finish`，客户端本轮新增 `finishTrip`）。
但这只是止损：列表徽章与库内 status 长期背离，且每次都要用户手点一下。

### 建议实现（两种，推荐 B+A 组合）

**方案 A：定时任务（推荐作为唯一真相来源）**

位置建议 `apps/server/src/common/scheduler/`（新增），在 `main.ts` 启动时挂载：

```
每 5 分钟（可配 AUTO_FINISH_INTERVAL_MS）：
  SELECT id, version FROM trip
   WHERE deleted_at IS NULL
     AND status IN ('PLANNED','ONGOING')
     AND end_date IS NOT NULL
     AND end_date < CURDATE()
  逐条调用 finish 的**内部实现**（不是 HTTP handler）
```

要点：

| 项           | 口径                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| 复用而非重写 | 抽出 `finishInternal(tx, tripId, expectedVersion, actorId, reason)`，HTTP 与定时器共用一个实现（禁止两份归档逻辑） |
| actorId      | 无自然人操作 → 取 `trip.createdBy`（保证审计有归属）                                                               |
| 审计 reason  | `TRIP_AUTO_FINISHED`（与手工的 `TRIP_FINISHED` 区分，便于对账）                                                    |
| 幂等         | 已 `FINISHED` 的数据不进入候选集；并发下 CAS 失败视为已完成，记 debug 不报错                                       |
| 失败处理     | 单条失败不影响其余；连续失败 N 次告警（沿用现有 notify/audit 通道）                                                |
| 开关         | `AUTO_FINISH_ENABLED`（默认开），便于灰度与回滚                                                                    |
| 多实例       | 若将来多进程，需加 DB 行锁或 `SELECT ... FOR UPDATE`（当前单 pm2 实例可先不加）                                    |

**方案 B：读时惰性流转（建议作为 A 的补充）**

`GET /trips` 与 `GET /trips/:id` 返回前，先对「该用户可见且已过期」的行程做一次 finish。
好处：定时器没跑（进程刚重启/任务挂掉）时，用户看到的也是正确状态。
代价：读路径写库 —— 必须放在事务里 + 失败降级为「只读不改」，绝不因流转失败让读接口 500。

### 验收用例

1. 把某行程 `end_date` 改成昨天（status=PLANNED）→ **不做任何操作**，等一个调度周期 →
   `GET /trips/:id` 返回 `status=FINISHED`、`myAccessLevel=HISTORICAL_READONLY`；
2. 该行程的 `changeLog` 有 `op=UPDATE` 记录，`auditLog` 有 `reason=TRIP_AUTO_FINISHED`；
3. 定时器重复跑两轮 → 不产生第二条归档记录（幂等）；
4. `AUTO_FINISH_ENABLED=false` → 不再自动流转（回滚开关有效）；
5. 未到 `end_date` 的行程不受影响；`CANCELLED` 不参与流转。

### 撤销条件

若业务改口「过期后仍要能继续编辑」，则退回纯手工标记 —— 前端 `FinishTripBar` 已就绪，
后端只需关掉开关，无需改客户端。

## P0-2 · 归档行程的照片仍可添加 / 删除

### 用户原话

> 「已完成的行程不能编辑信息**只能添加或删除回忆照片**」

### 现状（已核查代码，两道门都拦）

| 操作                                          | 实现                                                          | 归档后结果                                                                |
| --------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `POST /media/presign` + `POST /media/confirm` | `assertTripActiveWritable` → `assertTripMemberWritable`       | **403「该出行已归档，仅可查看」**                                         |
| `DELETE /media/:id`                           | `assertTripNotArchived` → 内部仍调 `assertTripMemberWritable` | **403**（`assertTripNotArchived` 的宽松只针对「行程已软删」，不针对归档） |

所以「回忆照片」这条路现在是**双向堵死**的：出行回来想补几张照片，传不上去。

### 建议改动（只放开 media 域，别的一律不动）

1. **`media.service.confirm`（登记）**：当 `tripId` 非空且成员 `accessLevel=HISTORICAL_READONLY` 时，
   **放行**登记，但写入审计 `action='media.upload_archived_trip'`、`severity='INFO'`；
2. **`media.service.presign`**：同上放行（否则前端拿不到上传位）；
3. **`media.service.remove`（删除）**：放行；删除权限口径不变（上传者本人或家庭户主）；
4. **其余域维持 403 不变**：`itinerary` / `checklist` / `expense` / `booking` 一律不放宽 ——
   「信息锁定」正是用户要的，别顺手放开。

实现建议：在 `media.service` 内新增一个专用于媒体的门
`assertTripMediaWritable(tripId, userId)`：只校验「是本行程成员 / 或创建者」，
**不校验** `accessLevel`；同时不要在 `common/auth/access-policy` 里改那四域共用的
`assertTripMemberWritable`（那条是四域同源的单点，动它会连坐）。

### 验收用例

1. 对 `FINISHED` 行程上传照片 → 200，`mediaAsset` 行 `tripId` 正确，`exifStripped=true`；
2. 删除自己刚传的照片 → 200；非上传者且非户主删除 → 403；
3. **同一条行程**改标题 `PATCH /trips/:id` → 仍 403（信息仍锁定）；
4. 归档行程新增安排 `POST /itineraries` → 仍 403；
5. 归档行程记账 `POST /expenses` → 仍 403（记账属信息，保持锁定）。

> ⚠️ 第 5 条需要产品确认：用户原话是「只能添加或删除回忆照片」，
> 所以记账也一并锁定。若产品希望「出行回来补记最后一笔」，需另行明确，
> 前端 `PhotoTab` / `ExpenseTab` 的门禁是分开的，改起来只是透传标志位。
