# 媒体存储接入说明（Media Storage）

> 适用版本：2026-10-26 起（派发单 D-2026-10-26-04）
> 一句话：**当前实现是「本地磁盘 + nginx 直出」**，将来换 COS/OSS/S3 只换一个 driver。

---

## 1. 当前链路长什么样

```
客户端 chooseImage
   ↓ ① POST /api/media/presign            （走 8 段链，需登录）
   ↓    ← { uploadUrl, fileKey, expiresIn }
   ↓ ② Taro.uploadFile(uploadUrl, file)   （multipart/form-data）
   ↓    uploadUrl = <MEDIA_PUBLIC_BASE_URL>/upload?fileKey=..&exp=..&sig=..
   ↓    → nginx 反代到 Node → 校验签名 → 落盘 OBJECT_STORAGE_ROOT
   ↓ ③ POST /api/media/confirm            （登记 media_asset + change_log）
   ↓ ④ GET  /api/media                    （列表 url = <MEDIA_PUBLIC_BASE_URL>/<fileKey>）
   ↓ ⑤ 读图 = nginx alias 直出（不耗 Node CPU）
```

为什么中间那跳是**自家端点**而不是「客户端直传桶」：

- 小程序 `Taro.uploadFile` **只能发 multipart/form-data POST**，不能 PUT 裸流，也不能发 Blob；
- 桶的「POST Object 表单」直传也能做，但要客户端多传 `formData`（改前端），且服务端拿不到字节 →
  EXIF 服务端剥离（M6 隐私要求）做不了；
- 走自家端点：字节在手 → EXIF 剥离天然可做，前端 0 改动，契约不变。

## 2. 配置（生产必读）

`.env`（`apps/server/.env`，600 权限）四处：

```ini
# ① 对外基址：既是回读前缀，也是收单端点父路径 —— 两者同源才不会「传上去但显示不出来」
MEDIA_PUBLIC_BASE_URL=https://api.familytripallinone.cn/media-files

# ② 上传位签名密钥（openssl rand -hex 32）
MEDIA_UPLOAD_SECRET=<64 位 hex>

# ③ 落盘根目录（独立路径，别放代码目录；nginx alias 必须指到同一个目录）
OBJECT_STORAGE_ROOT=/home/ubuntu/ft-media

# ④ 驱动（当前只有 local）
OBJECT_STORAGE_PROVIDER=local
```

缺 ①/② 时**服务照常启动**（不让一个功能缺配置把整个 API 拖死），但：

- 启动日志会打 `[family-trip] ⚠️ 媒体上传不可用：…`；
- `POST /media/presign` 返回 **HTTP 503 + code 5008**「媒体存储未配置：…」，
  **不再**返回假的 `https://upload.local/...`（那会让「上传失败」查很久）。

## 3. 换云对象存储（COS / OSS / S3）要改哪里

接口就三个方法（`src/common/object-storage/object-storage.ts`）：

```ts
export interface ObjectStorage {
  readonly kind: string;
  signUpload(args: { fileKey: string; mimeType: string; byteSize: bigint }): Promise<SignedUpload>;
  putObject(fileKey: string, data: Buffer, mimeType: string): Promise<void>;
  fetchObject(fileKey: string): Promise<Buffer>;
}
```

接入步骤：

1. 新增 `src/common/object-storage/cos-storage.ts`（或 s3/oss），实现上面三个方法；
   - `signUpload` 返回**桶的 POST Object 表单**地址 + `formData`（需扩 `SignedUpload`，纯加法），
     或直接复用「自家收单端点 + putObject 转存」——后者前端零改动，推荐先走这条。
2. `src/common/object-storage/index.ts` 里 `OBJECT_STORAGE_PROVIDER` 加分支（当前是
   `provider !== 'local'` 直接抛错，改成返回对应 driver）。
3. `.env` 设 `OBJECT_STORAGE_PROVIDER=cos` + 桶名/地域/AK/SK；`MEDIA_PUBLIC_BASE_URL` 改成 CDN 域名。
4. 老文件迁移：`rsync -a /home/ubuntu/ft-media/ <本地挂载或 rclone 目标>/`，fileKey 布局不变，直接对得上。
5. 若走桶直传（前端多传 `formData`）：改 `apps/client/src/utils/upload.ts` 一处，并把
   `media.service.stripExif` 改成「先下载再上传」链路（`fetchObject`/`putObject` 已具备）。

**不要**为了省事把云 drive 的逻辑写进 media 域：media 只认 `ObjectStorage`，别下沉。

## 4. 安全边界

| 面       | 现状                                                          | 说明                                                                 |
| -------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| 上传鉴权 | URL HMAC 签名（`fileKey + exp`，默认 900s）                   | 小程序不便带 Bearer 头；签名覆盖 fileKey，换 key 复用签名无效        |
| 目录穿越 | `safeMediaKey` 正则 + `path.resolve` 二次兜底                 | 禁 `..`、禁反斜杠、禁非 ASCII                                        |
| 同域 XSS | 扩展名白名单 + `nosniff` + 未知类型一律 octet-stream          | 上传的 `.html`/`.svg` 不会被当页面执行                               |
| 大小     | 收单端点 50MB + nginx `client_max_body_size 50m` + 库级 CHECK | 三处同口径，避免「传成功但 confirm 失败」                            |
| 覆盖写   | 上传位签名后 15 分钟内可覆盖同一 key                          | fileKey 含时间戳+随机段，实际不可猜；如需更严可改一次性 nonce        |
| 盗链     | 无                                                            | 图片 URL 公开可读（家庭相册场景）；如需防盗链，加 CDN 鉴权或短期签名 |

## 6. 已知限制（如实）

1. **单盘无冗余**：服务器盘坏 = 媒体全丢（靠快照兜底），无 CDN 加速；
2. **多实例不可用**：两个进程各写本地磁盘会分叉 —— 上多实例前必须换云存储或共享盘；
3. **头像已解耦家庭（2026-11-05 起）**：`media_asset.family_id` 放宽为 NULL，
   AVATAR 的 `presign` / `confirm` **不再要求 `familyId`、也不再校验家庭成员资格**，
   只校验账号本身 + `file_pending.ownerId` 归属。没有家庭的用户可正常改头像。
   - 上线顺序：先 `prisma migrate deploy`（新增迁移
     `20261105000000_media_asset_family_nullable`），再发新代码 —— 顺序反了会写 NULL 到 NOT NULL 列。
   - 家庭相册已按两重条件排除头像：`family_id IS NULL` + `fileKey` 前缀 `a/`
     （后者兼容改造前带 `familyId` 的旧头像行）。
4. **`confirm` 现在读 `purpose`（2026-11-05 起）**：请求可带 `purpose`，服务端以
   `file_pending.purpose` 为准做一致性校验，冲突则 422；不带则按 pending 处理（老客户端零影响）。
   `media_asset` 表仍**没有** purpose 列 —— 用途只记录在 `file_pending.purpose`
   （足够做孤儿清理与配额）；要按用途统计资产需另开单加列。
