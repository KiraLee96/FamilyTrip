## 零、一句话结论

各域用 `serializeRow(row, X_BIGINT_FIELDS)` **白名单**把 BigInt 转 string，但白名单**漏列**；单测跑的是 `MemoryTableDriver`（列以 JS number 落内存，`typeof v === 'bigint'` 恒 false），**漏列在单测里永远不暴露**；真 MySQL（Prisma）下这些列回的是 BigInt → `JSON.stringify` 抛 `TypeError: Do not know how to serialize a BigInt` → **HTTP 500 且响应体退化为 Nest 默认结构，不走信封**。

**系统性规律：凡是有 `version BigInt` 列的模型，白名单都漏了 `version`。**

### 1.4 精确根因

```prisma
// prisma/schema.prisma
model Trip {
  id        BigInt  @id
  familyId  BigInt  @map("family_id")
  createdBy BigInt  @map("created_by")
  leaderId  BigInt? @map("leader_id")
  version   BigInt  @default(1) @db.UnsignedBigInt   // ← 漏了
  ...
}
```

```typescript
// src/domains/trip/trip.service.ts:47
const TRIP_BIGINT_FIELDS = ['id', 'familyId', 'createdBy', 'leaderId']; // ← 少 version
```

`serializeRow` 只对白名单内的字段做转换：

```typescript
// src/domains/domain-context.ts:134
export function serializeRow(row: Row, bigintFields: string[]): Record<string, unknown> {
  const out: Record<string, unknown> = {};
  for (const [k, v] of Object.entries(row)) {
    out[k] = bigintFields.includes(k) && typeof v === 'bigint' ? v.toString() : v;
  }
  return out;
}
```

## 三、修复要求

### 3.1 P0-A 补齐白名单漏列（最小改动）

把上表漏列补进对应常量。**至少先修 `version` 一类**，它影响面最大且已实证。

### 3.2 P0-B HTTP 边界加 BigInt 兜底（建议同时做，防复发）

`serializeRow` 白名单是"逐处自觉"，天然会漏。建议在**唯一出网点**加一道与业务无关的护栏：

```typescript
// src/http/http-adapter.controller.ts（handle 末尾）
res
  .status(result.httpStatus)
  .json(JSON.parse(JSON.stringify(result.envelope, (_k, v) => (typeof v === 'bigint' ? v.toString() : v))));
```

收益：再漏列时退化成**"多返回一个字符串字段"**（客户端本就按 string 处理 id），
而不是 500 + 丢信封。**注意**：这不能替代 P0-A（显式类型正确性仍应由白名单保证），
两者是「治本 + 兜底」的关系。

### 3.3 P1 真 driver 冒烟纳入门禁

现状：`vitest` 全量 277/277 通过，但**没有一个用例跑 Prisma 驱动**，
所以这类缺陷零成本穿透。要求：

1. 至少一个**连真 MySQL** 的冒烟用例集（可用 docker / 本地实例），覆盖
   `POST /trips` → `GET /trips` → `GET /trips/:id` → `PATCH` → `DELETE` 的最小闭环，
   断言 **HTTP 状态 + 信封 `code` + 响应可序列化**（不必断言具体数据）。
2. 把 `.verify/audit-bigint-fields.cjs`（或等价实现）作为 CI 检查，漏列即红。
