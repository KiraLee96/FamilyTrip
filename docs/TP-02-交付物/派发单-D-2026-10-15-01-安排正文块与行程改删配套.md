## 一、P0（阻断）：itinerary 域支持 `blocks`

### 1.1 数据迁移

新建 `apps/server/prisma/migrations/20261015120000_itinerary_blocks/migration.sql`：

```sql
-- AlterTable
ALTER TABLE `itinerary_item`
    ADD COLUMN `blocks_json` TEXT NULL;
```

口径说明（勿自行发挥）：

1. `blocks_json` 允许 NULL：历史行留空即「无正文块」，前端按 `note` 兜底渲染，**不需要回填脚本**。
2. 用 TEXT 而非 JSON 列：与既有 `trip.destinationsJson` 同构，避免引入 Prisma 对 MySQL JSON 类型的额外差异面。
3. 不新增索引：正文块只随安排行整体读写，从不做块级查询。
4. `date/start_time/end_time` 等既有死列保持不动（纯加法迁移）。

对应 `prisma/schema.prisma` 的 `ItineraryItem` 增一行：

```prisma
  /// 安排正文块（富文本/图片，JSON 数组；NULL = 老数据只有 note）
  blocksJson String? @map("blocks_json") @db.Text
```

### 1.2 Zod schema（`itinerary.schema.ts`）

```typescript
/** 正文块单块上限：与前端 MAX_BLOCKS 一致（界面先拦一次，服务端独立校验） */
const blockText = z.string().min(1).max(2000);
const blockUrl = z
  .string()
  .max(512)
  .refine((u) => /^https?:\/\//i.test(u), { message: '链接只允许 http/https' });

export const itineraryBlockSchema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('text'), text: blockText }),
  z.object({ type: z.literal('quote'), text: blockText }),
  z.object({ type: z.literal('code'), text: z.string().min(1).max(500) }),
  z.object({ type: z.literal('link'), text: z.string().min(1).max(120), url: blockUrl }),
  // 入参只接受 assetId；url 是服务端派生字段，不接受客户端传入
  z.object({
    type: z.literal('image'),
    assetId: idInput,
    caption: z.string().max(120).optional(),
  }),
]);

/** blocks：数组上限 20，整体可空（undefined = 不更新；[] = 清空） */
export const blocksInput = z.array(itineraryBlockSchema).max(20).optional();
```

挂载点：

- `createItineraryItemSchema`：新增 `blocks: blocksInput`
- `updateItineraryItemSchema`：新增 `blocks: blocksInput`

⚠️ `updateItineraryItemSchema` 现有 `.refine(v => Object.keys(v).length > 1)` 保持不变 —— 前端更新时始终带 `version + title + startAt`，不会只提交 blocks 而误触发「没有需要更新的字段」。

**整体体积闸门**（防单行撑爆行/带宽，放在 service 写入前）：

```typescript
const BLOCKS_MAX_BYTES = 16 * 1024;
if (input.blocks !== undefined && JSON.stringify(input.blocks).length > BLOCKS_MAX_BYTES) {
  throw new AppError(ErrorCode.VALIDATION_FAILED, '正文块内容过大');
}
```

写入：

  data['blocksJson'] = JSON.stringify(input.blocks); // 整体替换语义；[] 写 '[]'

读取（列表与详情共用同一个投影函数，避免两处口径漂移）：

```typescript
/**
 * 行 → 出参：解析 blocksJson，并把 image 块的 assetId 解析为 url（方案 A）。
 * · NULL / '[]' / 解析失败 → 出参**不带 blocks 字段**（前端走 note 兜底）
 * · 解析失败的单个块 → 丢弃该块，不影响其余块（不因一块脏数据让整条安排 500）
 */
async function projectBlocks(tx: TxHandle, row: Record<string, unknown>): Promise<ItineraryBlock[] | undefined>;
```

图片 url 解析要求：

1. 批量取资产（一条 `id IN (...)` 查询，**不要 N+1**）：`deletedAt = null` 且 `familyId = 该行程的 familyId`。
2. `url = (process.env.MEDIA_PUBLIC_BASE_URL ?? '') + fileKey`，与 media 域 `list/confirm` **同一口径**（同一环境变量、同一拼接方式）。
3. `MEDIA_PUBLIC_BASE_URL` 为空时（本地开发）返回空串，前端自动降级占位卡 —— 前端两种模式走的是同一条分支，这里不需要特殊处理。

### 1.4 图片块越权校验（安全红线）

图片块引用的 `assetId` 必须同时满足，否则 **422 VALIDATION_FAILED**（不要静默丢弃后返回 200 —— 客户端会以为写入成功）：

1. 资产存在且 `deletedAt IS NULL`；
2. `media_asset.family_id = 该安排所属行程的 family_id`（跨家庭引用一律拒）。

参考实现位置：校验放在写路径（create/update）的事务内，与行程归属查询同事务，避免 TOCTOU。

### 1.5 老数据兼容（回归约束）

- `blocks_json IS NULL` → 出参不带 `blocks`；`note` 字段行为**一字不改**。
- 老客户端（不认识 blocks）读新数据：多出的 `blocks` 字段被前端类型系统忽略，不炸。
- 新客户端读老后端（本次迁移未上）：`blocks` 缺失 → 只渲染 `note`，**不白屏**（已实测：Mock 与真后端两条路径都覆盖）。

### 1.6 changeLog / 审计

沿用现有 `change()`：`block s 变更只记动作与时间，不把正文全文写进 change_log`（正文可能含酒店地址、订单号等个人敏感信息，进同步增量日志会扩大隐私面）。如需可检索摘要，写 `sha256(blocksJson)` 前 16 个十六进制字符。

## 二、P1（必做）：`DELETE /trips/:id` 的级联口径

### 2.1 现状（源码定位）

`apps/server/src/domains/trip/trip.service.ts` 的 `remove()`（约 216 行）：**仅软删 trip 行 + 写 changeLog**：

```typescript
await tx.db.update('trip', { id: tripId }, { deletedAt: now, updatedAt: now });
await this.change(tx, 'trip', tripId, t['familyId'] as bigint, tripId, 'DELETE', now);
```

### 2.2 风险（用户可感知的数据不一致）

1. **子域行未随之失效**：`itinerary_item` / `trip_member` / `trip_checklist_item` / `expense` / `booking` / `media_asset` 仍挂在已删除的 trip 上；子域查询只按 `tripId + deletedAt`，**不校验父 trip 是否已删** → `GET /itineraries?tripId=<已删行程>` 仍会返回安排，客户端直接按 tripId 打开会看到「幽灵行程」。
2. **邀请码仍有效**：`trip.invite_code` 未作废 → `POST /trips/join` 仍可能让外部成员加入一个已删除的行程（需确认 join 是否校验 `trip.deletedAt`；无论是否，这条都不该有第二种解释）。
3. 与家庭域 `dissolveFamily` 的既有做法是否一致，也需一并确认。

### 2.3 建议口径（推荐 A，二选一后在本单回执里写明）

**A. 删除事务内级联软删（推荐）**

在 `remove()` 的同一事务里，按域逐个软删并各写一条 changeLog：

```typescript
const now = await tx.db.dbNow();
await tx.db.update('trip', { id: tripId }, { deletedAt: now, updatedAt: now });
// 子域级联（软删，保留可审计痕迹）
for (const table of ['tripMember', 'itineraryItem', 'tripChecklistItem', 'expense', 'booking'] as const) {
  await tx.db.updateMany(table, { tripId, deletedAt: null }, { deletedAt: now, updatedAt: now });
}
// 邀请码作废：置 NULL（唯一索引 (invite_code, deleted_at) 允许多行 NULL）
await tx.db.update('trip', { id: tripId }, { inviteCode: null, inviteUpdatedAt: now });
```

`media_asset` 单独决策：**建议不随行程软删**（照片是家庭资产，行程删了照片墙应仍在「我的照片」里可见），仅在 `GET /media?tripId=<已删行程>` 时按父行程已删返回空集 —— 请后端确认后写回执。

**B. 最小改动**：不动删除逻辑，改为所有子域查询与 join 链路都必须校验父 `trip.deletedAt`。成本分散在每处查询，极易漏；**不推荐**。

### 7.2 §2.3 决策：采纳 **A**（删除事务内级联软删）

- **级联范围**：`tripMember` / `itineraryItem` / `tripChecklistItem` / `expense` / `booking` 五表在同一事务内软删；`change_log` 仅父实体一条 `DELETE`（与家庭域 `dissolveFamily` 既有做法一致，已核对）。
- **驱动适配说明**：派发单示例中的 `tx.db.updateMany` 在本代码库驱动层不存在（`TableClient` 契约只有逐行 `update(model, where, data)`），已等价改写为逐行 CAS `update`，语义不变（按 `tripId + deletedAt: null` 逐行命中后置 `deletedAt/updatedAt`）。
- **邀请码作废**：**未执行**——Trip 模型无 `invite_code` / `invite_updated_at` 字段（见 C3）。上一单邀请码三端点落地时必须同步作废（置 NULL）。
- **`media_asset` 最终决定：不随行程软删**（照片是家庭资产，行程删了「我的照片」墙应仍在）；对应查询侧口径：`GET /media?tripId=<已删行程>` 返回**空集**（C5）。另：itinerary 列表对已软删行程返回空集而非 404（C1），行程从来不存在时仍 404（不混淆「删过」与「没有」）。

### 7.4 §三 冻结项

**零改动**：`PATCH/DELETE /trips/:id` 信封形态、`version` 必传、`destinations` 整体替换、`startDate/endDate` 语义均照冻结表实现，未走任何评审变更。

### 7.5 顺带修复的既有阻断性 bug（P0 验收 B3 暴露，**非本单引入**）

`itinerary.controller.ts` 的 `itemRef` 将 `familyId/tripId` 硬编码为 `null`，权限网关第 5 段拿不到归属维度 → `GET/PATCH/DELETE /itineraries/:id` 全量 404 同形拒。该 bug 存在于 `HEAD`（前端仅在 Mock 下验收，真后端单资源路由从未打通）。已改为按资源行解析出的归属填充（同 media 域模式）。这是 P0「块编辑器保存」闭环的必要条件，否则读写链路断一半。

### 7.6 实现备注（与派发单示例的差异，均不偏离契约）

1. **change_log 摘要（§1.6）**：`ChangeLog` 模型无摘要列，加列即动 schema，与 §1.1「纯加法迁移、既有死列保持不动」冲突；且摘要是「如需」可选项。决定：**只记动作与时间，不写正文、不写摘要**（隐私红线守住），可检索摘要需求留待二期单独评审。
2. **图片 URL 解析方案**：采纳方案 A（批量 `id IN (...)` 一次查询，无 N+1）；单块脏数据（解析失败/资产已删/跨家庭）在读路径**丢块不 500**，写路径则 422 明确拒绝（§1.4），读写两侧口径按派发单分工落地。
3. **MEDIA 公网基址**：改由组合根唯一来源注入（`options.mediaPublicBaseUrl ?? env ?? 'https://media.local'`），media / itinerary 两域共用同一变量，杜绝两处口径漂移。
