## 零、为什么又开一单

2026-10-22 的真机验收里出现了两条「前端改不动」的问题，先把根因写清楚，避免再来一轮「以为是前端 bug」：

| 验收现象                                                   | 前端能不能自己解决 | 真实根因                                                                                                                      |
| ---------------------------------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 创建行程后「邀请外部成员」显示 **资源不存在（code 4040）** | ❌ 不能            | 后端 trip 域**没有** `/trips/:id/invite` 三条路由，请求未命中路由 → dispatcher 统一回 `4040`（见 §1.2）                       |
| 已完成的行程仍能改（尤其照片）                             | 🟡 部分            | 主流程各域（itinerary / expense / checklist / booking）已有 `HISTORICAL_READONLY` 拒写；**media 域完全没有该校验**（见 §2.1） |

前端这次的处置：

- 把「邀请码拿不到」从「资源不存在」这句会让人误判行程丢失的文案，改成明确的功能未就绪提示 + 重试入口；
- 把 `status ∈ {FINISHED, CANCELLED}` 的行程在详情页整体转只读（与服务端 `accessLevel` 口径对齐）。

但**这两条都不能替代后端**：邀请码必须服务端生成；只读必须服务端拒写。

## 一、P0 · 行程邀请三端点仍未落地（阻塞 GRP-02）

### 1.1 结论

`D-2026-10-14-02` 已把三条端点的路由、service 行为、迁移脚本、验收标准全部定稿，**至今未实现**。本单不重新设计，只要求按原单落地，并追加一条本单的实测口径（§1.3）。

| 端点                                        | 现状                 |
| ------------------------------------------- | -------------------- |
| `GET /trips/:id/invite`                     | ❌ 路由不存在 → 4040 |
| `POST /trips/:id/invite/reset`              | ❌ 路由不存在 → 4040 |
| `POST /trips/join`                          | ❌ 路由不存在 → 4040 |
| `trip.invite_code` / `invite_updated_at` 列 | ❌ 迁移未执行        |

### 1.2 4040 的产生链路（取证）

1. 前端 `apps/client/src/api/http.ts` → `getTripInvite()` 发 `GET /trips/{id}/invite`；
2. `apps/server/src/domains/trip/trip.controller.ts` 的 `routes` 数组里只有
   `/trips`、`/trips/:id`、`/trips/:id/finish`、`/trips/:id/members`、`/trips/members/:id`、
   `/trips/:id/leader`、`/trips/:id/leave` —— **没有 invite**；
3. 未命中路由进入 `common/middleware/dispatcher.ts` 的 `notFoundResult()`：

   ```ts
   /** 未命中路由 —— 与 404 同形，不泄露「该路径是否存在」 */
   function notFoundResult(): ChainResult {
     return {
       httpStatus: 404,
       envelope: { code: 4040, message: '资源不存在', data: null, meta: {} },
       reachedStage: 1,
     };
   }
   ```

4. 前端把信封里的 `message` 原样展示 → 用户看到「资源不存在」。

> 🔴 注意：`4040` 在本项目里是 `ErrorCode.NOT_FOUND`（`common/errors/error-code.ts`），
> 它同时被业务层用于「资源真的不存在」。因此**只看错误码无法区分「路由没实现」与「行程被删」**，
> 这正是这次误判的根源。接口落地后，前端不需要改任何解析逻辑。

### 1.3 本单追加要求

1. 严格按 `D-2026-10-14-02` §一～§五 实现，字段名/可空性/错误码一字不改；
2. 落地后在 PR 描述里贴 **`GET /trips/:id/invite` 的真实请求/响应体**（含 `code: 0`），作为前端切真后端的前置证据；
3. `POST /trips` 的响应体必须带 `inviteCode`（§六 6.1 第 1 条），否则前端"创建完立即进入邀请步骤"仍会空码；
4. 结束/取消的行程 `join` 必须回 `403 行程已结束，无法加入`（GRP-08），不能只靠前端隐藏入口。

## 二、P1 · media 域缺少「已结束行程不可写」校验

### 2.1 取证：同域对比

其余三个子域都有这道门（`accessLevel === 'HISTORICAL_READONLY'` → 拒写）：

| 文件                                     | 行号      | 校验                                        |
| ---------------------------------------- | --------- | ------------------------------------------- |
| `domains/itinerary/itinerary.service.ts` | 378       | ✅ HISTORICAL_READONLY 拒写                 |
| `domains/expense/expense.service.ts`     | 456       | ✅ HISTORICAL_READONLY 拒写                 |
| `domains/checklist/checklist.service.ts` | 579 / 618 | ✅ HISTORICAL_READONLY 拒写                 |
| `domains/booking/booking.service.ts`     | 454       | ✅ HISTORICAL_READONLY 拒写                 |
| `domains/media/media.service.ts`         | —         | ❌ 全文无 `accessLevel` / `tripMember` 读取 |

`media.service.ts` 只有 `assertFamilyMember`（是否家庭成员）与 `assertFamilyOwner`（删除权限），
判定粒度到**家庭**，没有到**行程成员状态**。

### 2.2 影响

- 行程 `FINISHED` 后，成员 `access_level` 已转 `HISTORICAL_READONLY`，但对 `tripId` 关联的照片
  **仍可 `presign` / `confirm` / `delete`** —— 历史记录并非真正只读；
- 前端这次已把照片 tab 的上传/删除入口整体收掉（`readonly` 覆盖 `PhotoTab`），
  但**改包/直接调接口可绕过**，与 B6「历史只读保留」的产品承诺不符。

### 2.3 要求

在以下三个入口补「若请求带 `tripId`，则校验当前用户在该行程的 `access_level`」：

| 方法                      | 校验点                                                                                         |
| ------------------------- | ---------------------------------------------------------------------------------------------- |
| `presign(userId, input)`  | `input.tripId` 存在时：`tripMember(tripId, userId)` 命中且 `access_level='ACTIVE'`，否则 `403` |
| `confirm(userId, input)`  | 同上（`input.tripId` 存在时）                                                                  |
| `remove(userId, assetId)` | 资产 `tripId` 非空时同上；`tripId` 为空（家庭照片）沿用现有 `assertFamilyOwner`                |

错误码与文案与其它域保持一致：`FORBIDDEN` / `该出行已归档，仅可查看`。

> 说明：`presign` 阶段前端还不一定知道 `tripId`（先取上传位再登记），因此
> **`confirm` 是必守点**，`presign` 有 `tripId` 时同样要拦。两处都做才闭环。

### 2.4 验收

1. 造一场 `FINISHED` 行程，用该行程成员身份 `POST /media/confirm`（带 `tripId`）→ `403 该出行已归档，仅可查看`；
2. `DELETE /media/:id`（资产属于已结束行程）→ `403`；
3. `ACTIVE` 行程的同一组操作 → 全部成功（回归不破）；
4. 家庭照片（`tripId` 为空）删除行为不变。

## 三、P2 · 地区字典下沉（建议，不阻塞本次上线）

### 3.1 现状

本次前端实现了「目的地地区选择」（验收反馈第 1 条），数据源是客户端内置的
`apps/client/src/utils/regions.ts`：34 个省级行政区 + 每省常用目的地城市（约 200 条）。

选内置而不是 `picker mode="region"` 的原因：该 mode 只在微信小程序端存在，H5 端无等价实现，
用它等于双端行为分叉（组件不 fork 是硬约束）。内置表两端完全一致，且离线可编辑。

代价也很明确：**行政区划表是静态数据被写进了发版包**——数据更新要发版，且内地全量 333 个
地级行政区划没有覆盖（当前只收常用目的地，缺的靠「搜索框直接输入原文」兜底）。

### 3.2 建议（二选一，都属纯加法）

- **方案 A（推荐）**：`GET /regions` 返回 `{ provinces: [{ province, cities[] }] }`，
  服务端读一份可热更的字典文件（JSON），客户端首次拉取后 `Taro.setStorage` 缓存 7 天，失败回退内置表；
- **方案 B**：客户端继续内置，但字典改为由后端产出的 JSON 在构建时注入（`copy.patterns` 打进包），
  至少保证「数据源单一」，仍需发版。

前端已把取数收敛在 `utils/regions.ts` 一个文件里（`PROVINCES` / `citiesOf` / `searchRegions` 三个导出），
换数据源不影响任何页面代码。

## 五、验收标准（逐条可测）

1. `GET /trips/:id/invite`（成员身份）→ `code: 0`，`data.inviteCode` 为 8 位 `/^[A-HJ-NP-Z2-9]{8}$/`；
2. 前端切真后端（`API_BASE_URL`），创建行程后**邀请步骤能显示真实邀请码**，不再出现 `4040`；

4. 同一账号二次 join → `alreadyMember: true`，`trip_member` 行数不变；
5. `FINISHED` 行程 join → `403`；非主导者 reset → `403`；非成员 GET invite → `403`；
6. §2.4 的 4 条 media 校验全过；
7. 回归：E7 CAS 冲突（409）、E8 退位、B6 结束后只读、家庭邀请码行为均不变；
