# 一、技术选型

## 1.1 总体技术栈

| 层             | 选型                                                        | 理由                                                                    |
| -------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- |
| 小程序端       | ✅ **Taro + React + TypeScript**                            | 多端编译，二期 Web 可复用大部分业务代码与组件                           |
| Web 端（二期） | **Vite + React + TypeScript**（或直接复用 Taro 的 H5 产物） | 与 Taro 同技术栈，组件与逻辑可复用                                      |
| 后端           | ✅ **NestJS + TypeScript**                                  | 全栈 TypeScript，与前端同语言；模块化架构清晰，装饰器风格对 C# 背景友好 |
| 数据库         | **MySQL 8.0**（主库）+ **Redis**（缓存/会话/分布式锁）      | 关系型数据结构清晰，事务可靠                                            |
| ORM            | **Prisma** 或 **TypeORM**                                   | NestJS 生态友好；Prisma 类型安全更佳                                    |
| 对象存储       | **腾讯云 COS**                                              | 微信生态兼容性好，自带图片处理                                          |
| CDN            | **腾讯云 CDN**                                              | 与 COS 同厂商，回源链路短                                               |
| 消息推送       | **微信订阅消息**                                            | 唯一合规触达渠道                                                        |
| 定时任务       | **BullMQ（Redis）**                                         | NestJS 官方推荐，与 Redis 复用                                          |

> **确定选型**：Taro（小程序 + 二期 Web）+ NestJS（后端），全栈 TypeScript

## 1.3 分层约定

| 层         | 职责                     | 注意                               |
| ---------- | ------------------------ | ---------------------------------- |
| Controller | 参数校验、鉴权、响应封装 | **必须做权限校验**，不可依赖前端   |
| Service    | 业务逻辑、事务边界       | 加密/解密、汇率折算在此层          |

# 二、数据库设计

## 2.1 设计原则

1. **软删除**：所有业务表带 `deleted_at`，物理删除仅用于合规场景。
2. **时间戳**：所有表带 `created_at` / `updated_at`，用于多端同步判定。
3. **ID 策略**：主键用 **雪花 ID（BIGINT）**，避免自增暴露业务量，且分库友好。
4. **权限公式落地**：`可见 ⟺ 属于自己的家庭 ∨ 属于自己参与的某次出行`，通过 `trip_member` 表统一承载。
5. **金额精度**：金额统一用 `DECIMAL(18,4)` 存储，避免浮点误差。

```sql
CREATE TABLE `trip` (

  KEY `idx_family_year` (`family_id`, `year`),
  KEY `idx_dates` (`start_date`, `end_date`)
) COMMENT='出行';

-- 出行目的地（一对多）
CREATE TABLE `trip_destination` (
  `id`        BIGINT       NOT NULL,
  `trip_id`   BIGINT       NOT NULL,
  `name`      VARCHAR(128) NOT NULL,
  `sort`      INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_trip` (`trip_id`)
) COMMENT='出行目的地';

-- 出行成员（含外部成员）★ 权限判定核心表
CREATE TABLE `trip_member` (
  `id`         BIGINT      NOT NULL,
  `trip_id`    BIGINT      NOT NULL,
  `user_id`    BIGINT      DEFAULT NULL COMMENT '用户ID；虚拟成员为NULL',
  `member_ref` BIGINT      DEFAULT NULL COMMENT '引用 family_member.id（虚拟成员用）',
  `is_leader`  TINYINT(1)  NOT NULL DEFAULT 0 COMMENT '是否主导者',
  `is_external` TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否外部成员（非主办家庭成员）',
  `joined_at`  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `deleted_at` DATETIME    DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_trip` (`trip_id`),
  KEY `idx_user` (`user_id`)
) COMMENT='出行成员（含外部成员）';
```

> **权限校验说明**
> 判断用户 U 能否访问资源 R：
>
> 1. 取 U 所属的 `family_id` 列表 → 若 R.family_id ∈ 该列表 → 放行
> 2. 取 U 参与的 `trip_id` 列表（`trip_member.user_id = U`）→ 若 R.trip_id ∈ 该列表 → 放行
> 3. 否则拒绝
>
> 注意：**私人资源**（私人清单、个人物品库）走独立校验：`owner_id = U` 或其 `managed_by = U`。

# 三、接口设计

## 3.1 接口规范

| 项       | 约定                                      |
| -------- | ----------------------------------------- |
| 协议     | HTTPS + JSON                              |
| 鉴权     | Header `Authorization: Bearer <token>`    |
| 响应结构 | `{ code: 0, message: 'ok', data: {...} }` |
| 分页     | `page` / `pageSize`，返回 `total`         |
| 时间格式 | ISO 8601（`2026-05-01T09:00:00+08:00`）   |
| 错误码   | 4xxxx 客户端错误，5xxxx 服务端错误        |

## 3.2 接口清单（按模块）

# 四、关键机制实现

## 4.1 字段级加密

### 4.1.1 方案

| 项       | 方案                                                 |
| -------- | ---------------------------------------------------- |
| 加密算法 | **AES-256-GCM**（带认证，防篡改）                    |
| 密钥管理 | 服务端 **KMS** 托管，按环境隔离（dev/staging/prod）  |
| 密钥轮换 | 支持多版本密钥（`key_version` 字段），新数据用新密钥 |
| 加密范围 | `booking.order_no`、`booking.order_link` 等敏感字段  |
| IV       | 每条记录独立随机 IV，与密文一起存储                  |

### 4.1.2 存储格式

```
密文存储结构（VARBINARY）：
[1 byte key_version][12 bytes IV][ciphertext][16 bytes tag]
```

### 4.1.3 解密权限

```
可见明文 ⟺ 用户是 booking.created_by
        ∨ 用户是 trip 的主导者（trip_member.is_leader = 1）
否则返回脱敏值（如订单号仅留后 4 位）
```

### 4.1.4 脱敏规则

| 字段     | 脱敏展示                     |
| -------- | ---------------------------- |
| 订单号   | `****1234`（保留后 4 位）    |
| 订单链接 | 不返回，提示"仅可见人可查看" |

## 4.2 汇率快照机制

### 4.2.1 流程

```
用户录入外币金额
   ↓
服务端查询当日汇率（先查 exchange_rate 表，miss 则调外部源并落库）
   ↓
记录：currency + amount + exchange_rate + rate_time + amount_base
   ↓
amount_base 固化，后续任何操作不重算
```

### 4.2.2 关键规则

| 规则       | 说明                                                      |
| ---------- | --------------------------------------------------------- |
| 快照时效   | 以录入当天汇率快照，不随汇率波动                          |
| 手动覆盖   | 用户可指定 `exchange_rate`，此时 `source='MANUAL'`        |
| 补录       | 若汇率缺失，标记 `amount_base = NULL`，前端提示"待补汇率" |
| 基准币变更 | 用户改 `base_currency` 时，提示是否重算（默认不重算历史） |

### 4.2.3 精度规则

| 场景 | 规则                                           |
| ---- | ---------------------------------------------- |
| 存储 | 金额 `DECIMAL(18,4)`，汇率 `DECIMAL(18,8)`     |
| 展示 | 按币种精度：JPY 0 位、CNY/USD 2 位             |
| 汇总 | 先按原始精度累加，最后统一四舍五入到基准币精度 |
| 舍入 | 统一使用 **ROUND_HALF_UP**                     |

## 4.3 多端同步

### 4.3.1 一期方案（轮询 + 时间戳增量）

```
客户端记录 lastSyncAt
   ↓
GET /sync/changes?since=lastSyncAt
   ↓
服务端返回该时间点后被修改的记录（按 updated_at 过滤）
   ↓
客户端合并（后写覆盖）
```

| 项       | 说明                                          |
| -------- | --------------------------------------------- |
| 判定字段 | 全部业务表 `updated_at`                       |
| 冲突策略 | 最后写入优先（Last-Write-Wins）               |
| 历史保留 | 关键表保留最近 1 个历史版本（`*_history` 表） |
| 触发时机 | 进入页面 / 下拉刷新 / 前后台切换              |

### 4.3.2 二期演进

- 数据量增大后，引入 **变更日志表（change_log）** 替代全表 `updated_at` 扫描
- 实时性要求提升后，引入 **WebSocket / SSE** 主动推送

## 4.4 提醒调度

### 4.4.1 任务生成

```
出行/事项创建或修改时
   ↓
按规则生成 reminder_task 记录：
  - 需预定事项 → BOOKING_D2(预定日-2) / BOOKING_D0(预定日) / TRIP_D0(出行当天)
  - 普通事项   → ITEM_D3(事项日-3) / TRIP_D1(出行前1天)
   ↓
写入 reminder_task (status=PENDING)
```

### 4.4.2 任务执行

```
定时任务每 5 分钟扫描一次：
  SELECT * FROM reminder_task
  WHERE status='PENDING' AND remind_at <= NOW()
   ↓
按 receiver 聚合（同一人同一时刻多条 → 合并为一条）
   ↓
调用微信订阅消息 API
   ↓
更新 status=SENT / FAILED，记录 sent_at
```

### 4.4.3 降级

| 情况           | 处理                                     |
| -------------- | ---------------------------------------- |
| 用户未授权订阅 | 不发送，改为应用内待办（`GET /todo`）    |
| 发送失败       | 重试 3 次（指数退避），仍失败标记 FAILED |
| 同一时刻多条   | 合并为一条，减少打扰                     |

## 4.5 图片存储

### 4.5.1 上传流程

```
客户端选图 → 本地压缩（长边 1920px, 质量 80%）
   ↓
POST /upload/sign 获取 COS 直传签名
   ↓
直传 COS（不经过业务服务器，省带宽）
   ↓
回调/前端上报确认，落库 image URL
```

### 4.5.2 多级规格

| 规格     | 尺寸   | 用途     |
| -------- | ------ | -------- |
| `thumb`  | 200px  | 列表     |
| `medium` | 1080px | 详情页   |
| `origin` | 原图   | 查看大图 |

> 使用 **COS 图片处理**（`?imageMogr2/thumbnail/...`）按需生成，无需预存多份。

### 4.5.3 成本控制

- **生命周期**：> 1 年的图片转低频存储，> 3 年转归档存储
- **分级加载**：列表永不加载原图
- **压缩前置**：客户端压缩是省流量的第一道闸

## 4.6 节假日抓取

```
定时任务：每年 11 月 1 日起，每周检查一次
   ↓
抓取国务院办公厅公告（或调第三方 API）
   ↓
解析出节假日 + 调休上班日
   ↓
写入 holiday 表（按 date 幂等 upsert）
   ↓
失败则保留旧数据，管理端告警
```

## 4.7 权限校验中间件

```typescript
// 伪代码：统一权限判定
async function checkAccess(userId: bigint, resource: Resource) {
  // 1. 家庭维度
  const families = await getFamilyIds(userId);
  if (resource.familyId && families.includes(resource.familyId)) return true;

  // 2. 出行维度（临时家庭）
  if (resource.tripId) {
    const trips = await getJoinedTripIds(userId);
    if (trips.includes(resource.tripId)) return true;
  }

  // 3. 私有维度
  if (resource.ownerId) {
    return resource.ownerId === userId || resource.managedBy === userId;
  }
  return false;
}
```

## 5.1 性能优化

| 项       | 措施                                                  |

| -------- | -------------------------------------------- |
| 鉴权     | JWT + 刷新机制                               |
| 越权防护 | 服务端强制校验（4.7 节），**不依赖前端隐藏** |

| 密钥     | KMS 托管，不硬编码                           |

| 日志     | 敏感字段脱敏，不落明文                       |
| 限流     | 网关层按 IP / 用户限流                       |
