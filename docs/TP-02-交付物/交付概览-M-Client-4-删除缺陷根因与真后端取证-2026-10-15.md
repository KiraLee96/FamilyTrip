## 一、缺陷 A（客户端，已修）—— 信封把「成功但无返回体」当异常

**根因**

`unwrap()` 把 `env.data === null` 判为异常（`ApiError(-1, '响应 data 为空')`），
而服务端 DELETE 的成功契约**就是** `data: null`
（`trip.controller.ts` → `({ data: null as never, meta: { updatedAt } })`）。

**影响**：真后端模式下 **9 个删除端点**全部「服务端已删成功、客户端抛异常」，
界面 catch 后弹提示、停在原页 → 用户看到「删不掉」。

**为什么此前 17/17 全绿仍漏掉**：那 17 例全在 **Mock 模式**跑，
而 mock 的 `deleteTrip` 直接 `splice` 内存数组、**不经过信封**，
信封口径只有真后端模式才会暴露。

**修复**（纯实现层，`ApiClient` 契约零改动）

- `request()` 新增 `opts.allowNullData`，在 `unwrap` **之前**分支：
  `code !== 0` 照旧抛错，`code === 0` 时允许 `data === null`；
- 新增 `requestVoid()`（语义 = 无返回体写操作），9 个 DELETE 调用点全部改走；
- **读路径判据原样保留** —— 单实体 `data === null` 仍是异常，
  否则 `getTrip` 会把空体当成功去 `toTrip({})`，造出 id 为空的幽灵行程。

**回归护栏**：`src/api/__tests__/envelope.test.ts` 6 例（桩掉 `Taro.request`，
直接驱动真实 `createHttpClient`）。

## 二、缺陷 B（服务端，已派发 D-2026-10-15-02）—— 真 MySQL 下响应无法序列化

首次把真 MySQL（prisma 驱动）拉起来跑，`POST /trips` 直接 500：

```
TypeError: Do not know how to serialize a BigInt
    at JSON.stringify (<anonymous>)
    at HttpAdapterController.handle (.../http-adapter.controller.js:64:39)
```

**根因**：`TRIP_BIGINT_FIELDS = ['id','familyId','createdBy','leaderId']`
**漏了 `version`**（schema 里是 `BigInt @db.UnsignedBigInt`）。

**端点矩阵（真 MySQL 实跑）**

| 端点                       | 结果                               |
| -------------------------- | ---------------------------------- |
| `POST /trips`              | 🔴 500，响应**不走信封**           |
| `GET /trips`               | 🔴 500，响应**不走信封**           |
| `GET /trips/:id`           | 🔴 500，响应**不走信封**           |
| `PATCH /trips/:id`         | 🔴 500，响应**不走信封**           |
| `DELETE /trips/:id`        | ✅ 200 `data:null`（不含 version） |
| `GET /itineraries?tripId=` | ✅ 200                             |
| `DELETE /itineraries/:id`  | ✅ 200 `data:null`                 |

**为什么 277/277 单测全绿仍漏掉**：单测跑 `MemoryTableDriver`，
列以 JS number 落内存，`typeof v === 'bigint'` 恒 false → 漏列零成本穿透。

**审计发现**：机械审计 28 个模型 / 63 处 `serializeRow` / 11 个常量 → **17 处漏列**；
规律是「**凡是有 `version BigInt` 列的模型，白名单都漏了 `version`**」。

🔴 **关键**：两个缺陷**叠加出同一症状**——即便客户端判据修好，
删完跳回列表仍会命中 `GET /trips` 的 500，界面照样显示「行程还在」。

## 六、环境踩坑沉淀（有复用价值）

| 坑                   | 结论                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 启动本机 MySQL       | 必须用受管 shell 直接传参；Git Bash 的 MSYS 会改写 `--datadir`，导致 datadir 回落 `E:\data\` 直接 Aborting           |
| `dist/` 增量构建损坏 | 症状是 `tsc` 退出 0 但产物缺 `dist/common/fx/`；**须 `rm -rf dist tsconfig.build.tsbuildinfo` 整目录重建**，勿信增量 |
| 本地代理劫持端口     | curl 一律加 `--noproxy '*'`，否则报 `upstream connect failed`，看着像服务没起                                        |
| 真后端登录           | **不需要微信**：H5 端 `obtainCode()` 合成 code，后端开发桩接受任意非空 code                                          |
| Taro H5 存储格式     | `localStorage[key] = JSON.stringify({ data: value })` —— 预注入登录态要用这个形状                                    |
